# uNdoqo V2.6: Secure digital fulfilment and receipt retrieval

This release **preserves** the existing website's HTML navigation, Contact form, logos, and colours. No live payment changes are required to test the database migration. **Keep PayPal in sandbox.**

## 0. Protect credentials

Do not put `.env`, PayPal API secrets, Supabase service-role keys or the administrator key into Git, screenshots, chat, browser JavaScript or frontend hosting variables. Earlier values were exposed in screenshots; rotate them if not already rotated. Keep `.env` excluded by `.gitignore`.

## 1. Back up Supabase before the migration

Open Supabase SQL Editor on the correct project, inspect the existing `db/001_commerce.sql` schema, and run **only** `db/002_secure_fulfilment.sql` once. Do not rerun the original migration. The new migration creates the private bucket `undoqo-digital-library`, `digital_assets`, and two service-role-only RPCs. It updates the existing `commerce_finalize_capture` RPC so new purchases get `active` entitlements only for enabled book assets. Existing purchases remain `pending_asset` until activation.

Verification:

```sql
select id, name, public from storage.buckets where id='undoqo-digital-library';
select product_id, display_name, enabled from public.digital_assets order by product_id;
select proname from pg_proc where proname in ('commerce_activate_asset','commerce_mark_refunded','commerce_finalize_capture');
```

The bucket must show `public = false`. Empty `digital_assets` is normal. Never add an `anon` SELECT policy on the bucket, `storage.objects`, or commerce tables.

## 2. Upload and activate **licensed PDFs**

Use Supabase Dashboard → Storage → `undoqo-digital-library` (private), then upload **only PDFs you have legal permission to distribute**. Use safe paths such as `books/book-001.pdf`. Prefer files under 50MB for this bucket and ensure `application/pdf` MIME type. PDFs are not bundled in this release; the storefront must not imply instant access until you add authorized assets.

Find catalog product IDs in `data/catalog.json`.

First register a PDF disabled:

```sql
insert into public.digital_assets(product_id,storage_path,display_name,enabled)
values ('book-001','books/book-001.pdf','Imibengo',false)
on conflict (product_id) do update
set storage_path=excluded.storage_path,display_name=excluded.display_name,enabled=false,updated_at=now();
```

Verify the file is uploaded, is the intended licensed work, and cannot be opened using a public bucket URL. Then activate:

```sql
update public.digital_assets set enabled=true,updated_at=now() where product_id='book-001';
select public.commerce_activate_asset('book-001');
```

The activation RPC updates paid entitlements from `pending_asset` to `active` for that product. The customer clicks **Refresh order status**, then **Download PDF**. Only server-issued signed storage URLs valid for 60 seconds are returned. Do not email or store those temporary URLs as permanent access links.

## 3. Verify paid receipt retrieval

On the same browser session where the sandbox checkout took place, open `/pages/order-status.html`, then **Print paid invoice**. The invoice-data function checks the stored `payments` capture, `orders` status and invoice number before presenting a printable invoice. In Chrome, choose Save as PDF. Current receipt-token access is tied to the browser session; a future customer account/verified email recovery system is needed for cross-device order history.

## 4. Configure PayPal sandbox webhooks after deploying the site

Localhost cannot receive normal PayPal webhooks. Deploy the Netlify preview under an HTTPS URL first. In PayPal Developer Dashboard → Apps & Credentials → your **Sandbox REST app** → Webhooks, register:

`https://YOUR-SITE.netlify.app/.netlify/functions/paypal-webhook`

Subscribe to `PAYMENT.CAPTURE.COMPLETED`. Copy the returned **Webhook ID** (not a URL) into the server-side Netlify environment variable `PAYPAL_WEBHOOK_ID`. Use the same sandbox PayPal app credentials as the checkout. Redeploy, then create a **new** sandbox purchase. Confirm the signed webhook is delivered and reflected in `paypal_webhook_events`. PayPal webhooks deliver independently of whether the customer's browser is open; the handler fetches canonical order details from PayPal and calls the existing idempotent database finalizer. An event duplicated by PayPal should not create another paid invoice or payment.

Note: PayPal dashboard simulation events may have different identifiers and may not reference a real order, so use genuine sandbox transactions for end-to-end recovery testing.

**Refund notifications are not automatically processed in V2.6.** `commerce_mark_refunded` provides a guarded server-side database function for reconciliation after a verified refund; never invoke it based solely on a client request or unverified notification. Refund webhook automation and staff review are a subsequent hardening task.

Official references: https://developer.paypal.com/api/rest/webhooks/rest/ and https://developer.paypal.com/payment-methods/webhooks/

## 5. SQL verification and duplicate safeguards

```sql
select o.id,o.status,o.total_usd,o.paypal_capture_id,
 p.provider_capture_id,p.amount,p.currency,p.raw_status,
 i.invoice_number
from public.orders o
join public.payments p on p.order_id=o.id
join public.invoices i on i.order_id=o.id
order by o.created_at desc limit 20;

-- These should return ZERO rows:
select provider_capture_id,count(*) from public.payments group by provider_capture_id having count(*)>1;
select order_id,count(*) from public.invoices group by order_id having count(*)>1;
select order_id,product_id,count(*) from public.digital_entitlements group by order_id,product_id having count(*)>1;
```

For real end-to-end testing, replay the same verified sandbox webhook from PayPal's webhook delivery history and verify the existing row counts do not increase. The SQL function's existing `FOR UPDATE` and duplicate-capture check protect concurrent callbacks. Test a failed/declined order, a repeated capture, and a refund against a staging database before production.

## 6. Run tests and deploy

From your existing Git checkout (do not overwrite `.git` or `.env`):

```powershell
node --test tests/*.test.js
npx netlify-cli dev
```

Use a dedicated branch `feature/v2.6-secure-fulfilment`, pull request, Netlify deploy preview, and sandbox tests before merging. To test storage downloads your Supabase project must have migration 002 and at least one uploaded licensed PDF. Browser and live external service tests remain required; static source tests cannot prove webhook delivery or storage permissions in your account.

## 7. Remaining production items

* PayPal webhook delivery confirmation and retries in deployed HTTPS environment
* Automated customer emails (requires a verified sender/domain and email service)
* Customer authentication and cross-device secure receipt recovery
* Refund reconciliation and chargeback handling; invoices and tax/legal review
* Live FX quote provider and agreed expiry/rounding policy (current rate is fixed for sandbox)
* Admin identity-based permissions rather than a shared key
* Operational backups, monitoring, abuse/rate limiting and end-to-end security checks
