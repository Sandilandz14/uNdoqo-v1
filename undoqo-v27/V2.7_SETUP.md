# uNdoqo V2.7 — Sandbox payment recovery and licensed PDF activation

This package builds directly on the working V2.6 website. It deliberately does not change the homepage, logos, navbar, Contact form, bookstore prices, PayPal checkout, or invoice styling. It adds secured *sandbox-only* payment reconciliation and private-library activation controls to the existing administrator page.

## Important: Back up and keep existing transactions

- Keep `PAYPAL_MODE=sandbox` until a separate production security review is complete.
- Preserve `.git` and your local `.env`; never commit API keys. Rotate any secrets exposed previously in screenshots.
- Back up the existing Supabase project before deploying changes. **Do not rerun** migrations 001 or 002 if already applied.
- The V2.7 features add no SQL tables or migrations. The existing V2.6 four functions and `digital_assets` private bucket are prerequisites.
- Do not make new sandbox payments to reconcile old ones, and do not run an unconditional SQL `UPDATE orders SET status='paid'`.

## 1. Install V2.7 safely

1. Make a Git branch from the latest working commit: `git switch -c feature/v2.7-recovery-asset-admin`.
2. Copy the release website files into the working repo **without overwriting** the existing `.git` directory and `.env` file. The ZIP unpacks under `undoqo-v27/`.
3. Review `git diff` (especially under `netlify/functions`, `pages/orders-admin.html`, and `js/admin-orders.js`).
4. Run `node --test tests/*.test.js` and `npx netlify-cli dev`.
5. Open `http://localhost:8888/pages/orders-admin.html` and type the private `UNDOQO_ADMIN_API_KEY` (minimum 32 characters, server-side environment only).

## 2. Reconcile past sandbox orders — no new charge

The administrator page now has **Inspect capture** and **Reconcile verified capture** actions. For each PayPal order ID below, first inspect.

- `1XF675336S976931` — R1,700 / USD 100.35, was pending
- `7PC24518BB164563` — R1,300 / USD 76.74, was pending
- `1XP58153FD424391` — R1,300 / USD 76.74, was pending

**What Inspect does:** It reads the existing Supabase order; calls PayPal's `GET /v2/checkout/orders/{id}`; validates one completed capture, the exact internal order `custom_id`, the saved currency and amount. It does not call the PayPal capture endpoint.

**What Reconcile does:** Only after inspection and explicit administrator confirmation, it retrieves the PayPal record again, rechecks the values, and calls the existing idempotent `commerce_finalize_capture` RPC. The RPC should create payment/invoice/entitlement records together. A completed order with the same capture is safe to process again; a different capture is rejected.

If PayPal reports `APPROVED`, `CREATED`, no captures, several captures or amounts that do not match the stored order, the tool refuses reconciliation. **Do not attempt to charge again.** Confirm the status in PayPal and investigate manually.

### SQL verification

```sql
select o.id,o.status,o.total_zar,o.total_usd,o.paypal_order_id,o.paypal_capture_id,
       p.provider_capture_id,p.amount,p.currency,p.raw_status,i.invoice_number
from public.orders o
left join public.payments p on p.order_id=o.id
left join public.invoices i on i.order_id=o.id
where o.paypal_order_id in ('1XF675336S976931','7PC24518BB164563','1XP58153FD424391')
order by o.created_at desc;
```

For each genuinely captured order, expect `paid`, a matching non-null capture ID, a single invoice, and USD amount equal to PayPal. Orders not actually captured must remain pending.

## 3. Upload and activate one licensed PDF

Your most recent verified purchase includes `book-015`, `book-013`, and `book-011`, all initially `pending_asset`.

1. Confirm that you possess the legal distribution rights for a particular PDF. **Do not upload an unlicensed title.**
2. In Supabase → Storage → **private** `undoqo-digital-library`, upload a PDF under e.g. `books/book-011.pdf`.
3. In `/pages/orders-admin.html` under **Digital library registration**, enter its real `productId` (see `data/catalog.json`), exact bucket-relative file path, and a display name.
4. Click **Register disabled PDF**. The backend checks the object exists, verifies its PDF MIME metadata, then creates an inactive registry row. Existing rows cannot be casually overwritten.
5. Inspect the uploaded PDF and confirm it is the correct, lawful document. Under **Activate verified PDF**, submit its product ID and confirm.
6. Activation checks the storage object again, enables the registry entry and updates matching paid entitlements through `commerce_activate_asset`.
7. On a paid buyer's `/pages/order-status.html`, click **Refresh order status**. The product should be active and provide **Download PDF** with a one-minute signed URL.

Only active entitlements on paid orders are allowed to request signed URLs. The bucket must stay private and no anon public-read policy should be added.

### Verify storage and entitlements

```sql
select product_id,display_name,storage_path,enabled from public.digital_assets order by product_id;
select order_id,product_id,status from public.digital_entitlements
where product_id in ('book-015','book-013','book-011') order by product_id;
select id,name,public from storage.buckets where id='undoqo-digital-library';
```

## 5. Automated acceptance vs. live checks

The local suite verifies source/syntax, permissions, refusal of unsafe captures, and a mocked PayPal/Supabase reconciliation. It does **not** prove live PayPal GET responses, actual Supabase Storage metadata, webhook delivery, or entitlement download in your accounts.

Before enabling real payments, still complete: end-to-end webhook retries and duplicate replay; refunds; automatic email delivery; user-based admin authentication/MFA; rate limiting; cross-device receipt authentication; live FX quote service; secure backups and monitoring.
